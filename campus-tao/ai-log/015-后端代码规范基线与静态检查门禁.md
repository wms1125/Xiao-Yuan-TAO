# ai-log 015 · 后端代码规范基线与静态检查门禁

> 里程碑：M9（工程流水线） ｜ 主题：spotless 基线格式化、verify 阶段门禁接入、离线仓库同步 ｜ 记录方式：AI 辅助留痕

## 里程碑目标

上一轮（ai-log 014）完成了前端这一半：Prettier 基线格式化 + ESLint 10 扁平配置 + `verify.bat` / CI 门禁。当时在"未纳入本轮（如实记录）"里明确留了一条：**后端 spotless/checkstyle 尚未落地**。

本轮就是把后端这一半按同一套顺序补上：

1. 先让后端 Java 代码整齐到"开规则不会满屏红"（基线格式化，独立成一个纯机械提交）；
2. 再让规则真正成为门禁（`spotless:check` 绑定 `verify` 阶段，随 `mvn verify` 生效）。

与前端最大的不同在于**格式化引擎的选型不能照抄**：前端用 Prettier 全量重排是合理的（PrintWidth 只影响折行），但后端若直接套 `google-java-format`，会把项目既有的 **4 空格缩进压成 2 空格**，等于用一版官方风格覆盖掉项目的既有风格。因此本轮的关键动作不是"选一个格式化器"，而是**先用实测数据量出每个候选的改动面，再决定从哪里起步**。

**关键指标**：google-java-format 方案 **346 文件 / 29008 增 32945 删**（且改变缩进风格）→ 弃用；最终方案 **250 文件 / 1023 增 1004 删**，且**全部为机械改动、可证明无语义变化**（249/249 文件哈希一致）。

## 关键决策与取舍

| 决策点 | 选择 | 备选方案 | 取舍理由 |
|--------|------|----------|----------|
| 用哪个格式化引擎 | **spotless + 三项"卫生类"步骤**：`removeUnusedImports`、`trimTrailingWhitespace`、`endWithNewline` | `google-java-format` / `eclipse` / `palantir-java-format` 等真正的代码重排器 | **先量化再决策**：实测 `google-java-format` 会改写 **346 个文件 / 29008 增 32945 删**，并把 4 空格压成 2 空格——与 `.editorconfig` 的 `[*.java] indent_size=4` 及上游 RuoYi 风格冲突，改完还要把缩进约定一并改掉，噪声远超收益。本项目要的是"能真正拦人、又不误伤"的门禁，不是一次全量重排版 |
| 门禁口径定在哪 | **只查"客观事实"（未使用 import、行尾空白、文件末尾换行）** | 连缩进宽度、括号位置、折行策略一起管 | 缩进/折行属"风格口味"，一旦纳入门禁，就等于要求所有后续改动都服从某一个格式化器；而"有未使用 import""行尾有多余空白"是**无争议的事实**，任何人都无法反驳，也永远不会误伤正常代码 |
| 行尾怎么处理 | **沿用 spotless 默认 `PLATFORM_NATIVE`** | 显式 `lineEndings = LF`（贴合 `.editorconfig`）/ `GIT_ATTRIBUTES` | 仓库根 `.gitattributes` 是 `* text=auto`，工作区检出为 CRLF。若强制 `LF`，每个文件都会被整文件重写，产生"假 diff"。实测抽查 60 个改动文件仍为 CRLF——**diff 里只有真实格式变化**。这与前端 Prettier 的 `endOfLine:'auto'` 是同一个判断 |
| 门禁绑定在哪个阶段 | **`spotless:check` 绑定 `verify`** | 绑定 `validate` / `compile`；或干脆不绑、只在脚本里显式调用 | 本仓库已有先例：`jacoco:check` 就绑定在 `verify` 阶段。绑定后**CI 的 `mvn -B verify` 自动获得该门禁，不需要增删任何 CI 步骤**，`verify.bat` 也无需新增步骤（第 3 步即 `mvn verify`）。绑 `validate` 虽然更早失败，但与既有门禁的绑定口径不一致，且会让每一次 `mvn compile` 都因格式问题中断，收益不抵扰动 |
| `apply` 要不要绑生命周期 | **不绑，人工执行 `mvn spotless:apply`** | 把 `apply` 绑到 `compile`，实现"构建即自动格式化" | "边构建边改源码"会让违规在构建过程中被悄悄改掉，**门禁失去举证意义**（无法回答"交付的这一版是否本来就是干净的"）。保持 `apply` 手动，才能让 `check` 的通过具备证据价值 |
| 是否叠加 checkstyle | **不叠加，单用 spotless** | spotless + checkstyle 双保险 | checkstyle 需要另写一份"既要满足 345 个上游文件、又要有约束力"的规则集，调优成本高；且它最常用的 `UnusedImports` 与 spotless 的 `removeUnusedImports` 职责重叠。spotless 还多一项关键能力：**`apply` 可一键自修复**，运维与新人上手成本更低 |

## 踩坑与解决

| 现象 | 根因 | 解决 |
|------|------|------|
| 离线 `-o` 下 `mvn verify` 找不到 spotless 插件 | spotless 及其全部构件（`spotless-lib`、`spotless-lib-extra`、`durian-*`、`google-java-format` 等）不在随包离线仓库 `.tools/m2-repo` 里 | 用 `mvn dependency:get` 联网抓取到 `.tools/m2-repo`，随后清理 **42** 个 `_remote.repositories` / `*.lastUpdated` 标记文件（这两类文件会让离线模式判定"构件来源仓库不匹配"而拒用），再实测离线 `spotless:check` 通过 |
| 直接套 `google-java-format` 会改动全仓库 | 它的缩进是硬编码 2 空格，且会重排全部换行 | 先量化：346 文件 / 29008 增 32945 删。据此改选"零争议"的卫生类步骤，改动量降到 250 文件 / 约 1.0k 行 |
| 担心格式化顺手改了行尾，把 diff 污染成"整文件重写" | 若显式指定 `lineEndings`，工作区 CRLF 会被整体改成 LF | 用 spotless 默认 `PLATFORM_NATIVE`（Windows = CRLF，与检出状态一致），并**抽查 60 个改动文件确认仍为 CRLF** |
| 担心 spotless 的增量缓存把违规"缓存掉"，导致负向验证假通过 | spotless 在模块 `target` 下维护 index 缓存 | 该缓存**按文件内容哈希**判定，文件一旦改动即失效。实测注入违规后 `mvn verify` 确实失败，缓存未干扰 |
| 已运行的后端进程会锁住发行 jar，导致 `mvn verify` 的 package 阶段失败 | Windows 下 `ruoyi-admin.jar` 被 `java -jar` 占用，`clean` 无法删除 | 校验前先停后端（`verify.bat` 第 1 步本身有"独占打开"方式的占用预检，命中即提示并跳过后端阶段）；本轮为人工先停 8080 / 8088 |
| 基线改动的"纯机械"结论需要可验证的依据，不能只靠肉眼 | 249 个文件的 diff 无法逐个人工核对 | 写脚本做**语义等价校验**：对每个文件剔除"全部空白字符与 import 行"后与改动前版本比对 SHA-256，**249/249 全部一致** |

## 验证证据

1. **候选方案改动面（实测，用于选型）**：
   ```
   google-java-format（4 空格→2 空格，全量重排） → 346 文件 ｜ 29008 增 / 32945 删   ← 弃用
   spotless 卫生类三项（本项目选定）            → 250 文件 ｜ 1023 增 / 1004 删      ← 选定
       ├─ Java 源码：249 文件 ｜ 997 增 / 1004 删
       │    ├─ 纯行尾空白改动：242 文件
       │    └─ 仅删未使用 import：7 文件（BigDecimal ×2、List ×2、PathVariable、HttpStatus、Param）
       └─ 根 pom.xml：26 行纯新增（0 删除，为配置与注释）
   ```

2. **基线"纯机械"的语义等价校验**：
   ```
   对 249 个改动文件：剔除全部空白字符与 import 行 → 与 HEAD 版本比对 SHA-256
   结果：249 / 249 一致（0 个文件存在语义差异）
   ```

3. **行尾未被改写（抽样 60 个改动文件）**：
   ```
   CRLF = 60 ｜ LF-only = 0
   ```

4. **门禁有效性（正 / 负向）**：
   ```
   正向：mvn -o -B spotless:check
         → 345 个 Java 文件全部 clean（0 needs changes）；退出码 0

   负向：在 CampusCartController.java 注入
         ① 1 条未使用 import：import java.util.HashMap;
         ② 1 行行尾空白
         执行 mvn -o -B verify
         → BUILD FAILURE，退出码 1
         日志：打印该文件违规 diff，并提示
               "Run 'mvn spotless:apply' to fix these violations."
         回滚探针后 spotless:check 恢复通过（退出码 0）
   ```

5. **门禁确实随 `mvn verify` 生效（绑定验证）**：
   ```
   [INFO] --- spotless:2.44.3:check (spotless-check) @ ruoyi          ---
   [INFO] --- spotless:2.44.3:check (spotless-check) @ ruoyi-common   ---

   （framework 45 / quartz 20 / generator 13 / admin 25，合计 345 文件）
   ```

## 遗留与后续

**未纳入本轮（如实记录）**：
- **检查范围仍偏"卫生类"**：本轮只查未使用 import 与空白，未涉及缩进、命名、复杂度等。若要引入更强的规则集，路径是先把 `google-java-format` 这类全量重排单独成一次提交（并同步修订 `.editorconfig` 的缩进约定），再在其上开门禁——**顺序不能颠倒**，否则仍会回到"要么全量整改、要么门禁形同虚设"的两难。
