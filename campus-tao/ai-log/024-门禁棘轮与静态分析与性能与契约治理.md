# 024 · 评估复评 7 项扣分逐条治理（门禁阈值、静态分析、性能、契约）

## 1. 目标与结论
对《企业级评估报告》复评结论（87/100）中点名的 7 项扣分逐条治理。核心是两处「门禁形同虚设」：
阈值停留在实测值下方 20~30 个点、以及语义级静态分析完全缺位。

**结论**：7 项中 5 项本轮闭环（阈值棘轮、静态分析、性能基准、契约归档、文档矛盾），
剩 2 项（UI 截图取证、制品归档）如实记入「未纳入本轮」。过程中**新发现 3 条此前不可见的真实缺陷**。

## 2. 关键实现

### 2.1 覆盖率门禁阈值棘轮上调（3 处配置 + 1 处 CI 注释 + 2 处文档）
- 后端 `ruoyi-system/pom.xml`：行 `0.55 → 0.70`、分支 `0.40 → 0.62`。依据 `jacoco.csv` 独立实算 **行 74.80%（1054/1409）/ 分支 67.32%（346/514）**。
- 前端 `vitest.config.js`：`40/55/45/45 → 68/72/67/64`。依据 `test:coverage` 实测 **行 73.27 / 语句 71.62 / 分支 68.10 / 函数 76.32**。
- 余量刻意只留 4~5 个点（而非原先的 20~30 个）：只为吸收无关改动的正常抖动，不再容纳「20 点级别的覆盖率塌方」。
- 注释由「停在旧实测值」重写为「历史演进链 + 本次实测依据」；`ci.yml` 前端 vitest 步骤注释一并修正。

### 2.2 后端静态分析接入（Checkstyle + SpotBugs，此前只有 Spotless 管格式）
- **Checkstyle**（`maven-checkstyle-plugin` 3.6.0 + `checkstyle` 10.21.4）：只启用**客观事实类**规则——通配符 import、重复 import、未使用局部变量、`NeedBraces`、空 `catch`、空块。**不含任何排版/命名风格偏好**，避免与 Spotless 重复报告同一问题。
- **SpotBugs**（`spotbugs-maven-plugin` 4.9.3.0，`effort=Max` + `threshold=Medium`）：字节码级语义分析。排除规则逐条写明理由（`domain/**` 纯 POJO 与 JaCoCo 排除口径一致；`EI_EXPOSE_REP/REP2` 是本项目 `Date` 在请求/响应边界的惯用写法）。
- 三者**作用域均限定 `com/ruoyi/campus/**`**，脚手架属上游债务不计入——与前端「全仓 0 error + 自有目录 0 warning」两档口径同构。
- 均绑定 `verify` 阶段；**不提供自动改写**，避免「边构建边改源码」使门禁失去举证意义。
- **负向验证**：注入 5 类违规 → 规则逐条命中（9 处、`BUILD FAILURE`、退出码非 0）；移除后 `0 Checkstyle violations`。

### 2.3 性能基准（先造数，再 EXPLAIN，再前后对照）
- `perf/bench-db.sql`：用 `CREATE TABLE ... LIKE` 在**独立库 `campus_tao_perf`** 复刻表结构后造数（5 万商品 / 5 万订单 / 10 万订单项），**不触碰交付库**。
- `perf/idx-candidate.sql`：4 条复合索引（过滤列 + `create_time`）前后对照。
- `perf/bench_http.py`：纯标准库并发压测（自研以守住「交付包无网可跑」约束），6 条接口路径取自归档 OpenAPI 规格。
- 报告 `docs/perf-report-v1.0.21.md`。

### 2.4 接口契约归档 + 门禁
- 归档规格 `docs/openapi/campus-tao-openapi.json`（194 path / 218 操作），由运行时 `/v3/api-docs` 导出；`SwaggerConfig` 标题与描述由脚手架占位文案改为校园淘实际契约。
- `tools/verify_openapi.py`：比对归档与运行时的 **path×method 与 operationId**，并校验规格版本与 `application.yml` 一致。**刻意不比对整份 JSON 文本**——键序/空白差异会产生误报。
- CI 的 `e2e` job 新增契约门禁步骤。

## 3. 本轮抓到的真实缺陷（三条，均为此前不可见）

1. **两处装箱拆箱往返（真实缺陷，SpotBugs 成果）**：`CampusAftersaleServiceImpl` 的 `type == null ? 1 : type` 与
   `CampusReviewServiceImpl` 的 `rating == null ? 5 : rating`——三元表达式混用 `int` 与 `Integer`，JLS 规定按二进制数值提升统一为 `int`，导致「拆箱 → 立即重新装箱」。
   改为 `Integer.valueOf(...)` 显式装箱。**接入 SpotBugs 之前，这类问题在源码上完全看不出来。**

2. **离线依赖仓库缺构件（交付缺陷）**：`.tools/m2-repo` 缺少 Spring Boot 4 拆分为独立模块后的
   `spring-boot-flyway` 与 `flyway-core` / `flyway-mysql`——它们只存在于开发机全局 `~/.m2`。
   **后果**：`verify.bat` 默认的 `-o` 离线构建在干净机器上会失败，与「无网可完整构建」的交付承诺相悖。
   首次 `-o clean verify` 正是在 ruoyi-admin 阶段以缺构件失败才暴露的——**离线构建本身即是这类缺陷的检测手段**。

3. **性能瓶颈：全表扫描 + 四处 filesort**：「商品管理」（按 `seller_id`）**无任何可用索引，全表扫描 49,628 行**；
   所有 `ORDER BY create_time DESC` 均 `Using filesort`，商城列表**只要 20 条却先回表 24,814 行再排序**。
   候选复合索引后：商品管理 **49,628 行 → 100 行（48×）**、耗时 10.50ms → 0.219ms；filesort 全部消除并转 `Using index`。

## 4. 验证
- **后端离线全链路**：`mvn -B -o clean verify`（`-o` 强制离线，同时验证离线仓库完整性）→ **BUILD SUCCESS（43.0s）**，
  `Tests run: 280, Failures: 0, Errors: 0, Skipped: 0`；覆盖率门禁（新阈值 70/62）通过；`0 Checkstyle violations`；SpotBugs `check` 通过。
- **前端**：`npm run test:coverage` 在**新阈值 68/72/67/64 下通过**，`Test Files 12 passed`，行 73.27 / 语句 71.62 / 分支 68.10 / 函数 76.32，退出码 0。
- **OpenAPI 契约**：归档 vs 运行时**完全一致**（218 操作逐一匹配，版本与 `application.yml` 一致）；负向验证删掉一条 path → FAIL + 退出码非 0 + 诊断精确。
- **HTTP 性能**：1/10/40 三档并发，40 并发达 **3,961 QPS / p99 21.8ms / 错误率 0.0%**，延迟随并发次线性增长。
- 离线仓库补件后重跑 `-o` 构建成功，证明**交付包仍满足「无网可完整构建」**。

## 5. 未纳入本轮（如实记录）
- **候选索引 DDL 未落地交付库**：索引属结构变更，应由版本化迁移（`V4__product_order_indexes.sql` + `U4`）管控，不由一次压测脚本顺手改掉交付库。
- **性能未测写路径**（下单/支付属资金路径，正确性由并发一致性用例覆盖，但未做吞吐压测）与**长稳压测**（>1h）；HTTP 层数字基于演示库规模，不代表大数据量下的延迟。
- **UI 浏览器截图证据**：本轮收尾时**已补齐**——`docs/evidence-v1.0.21/`（11 场景，含 v1.0.16~v1.0.20 的收货地址/收藏/站内信/购物车/商品管理 5 页新增覆盖），三服务在线取证 + 逐张 `get url` 回显自身路径 + 视觉核验。**仍未纳入**：admin 卖家视角、交互动作结果、响应式/移动端、多浏览器。
- **制品归档（GitHub Release）未做**：交付仍为「从源码构建」，尚未提供「取制品即用」的 jar + 校验和。

## 6. 方法论小结
- **门禁的价值在于"离实测值有多近"**：阈值 55% 而实测 74.80%，看似宽松是「留有余地」，实际是门禁对 20 点塌方无感。
  棘轮规则要真正生效，余量必须收窄到只够吸收正常抖动——**宽松的门禁和没有门禁，在防退化上是等价的**。
- **静态分析要按"客观事实"起步，不要按"风格偏好"起步**：Checkstyle 若一上来就启用命名/行宽/缩进类规则，会产出大量与 Spotless 重叠的风格告警，
  结果只能靠关闭规则让构建通过——**门禁从第一天起就变成了摆设**。只启用"命中即确定是缺陷"的规则，才能让它长期可用。
- **小表上做 EXPLAIN 等于没做**：演示库几十行，MySQL 必然全表扫描，既证明不了索引有效，也暴露不了索引缺失。
  造出有统计意义的规模（本案 5 万行）是性能结论可信的前提；同时用 `CREATE TABLE ... LIKE` 复刻结构并放到独立库，才能既可信又不污染交付数据。
- **离线构建是缺陷的检测手段，不只是构建方式**：本轮两个交付缺陷（缺 flyway 构件）不是"看"出来的，而是 `-o` 跑失败"压"出来的。
  若一直联网构建，`~/.m2` 会静默补全缺失构件，缺陷将一直潜伏到干净机器上才爆发。
- **契约归档要比对骨架，不要比对文本**：比对整份 JSON 会被键序/空白差异打乱产生误报，比 path×method + operationId 才能既准确又不误报。
- **"刻意不做"也要写进未纳入**：索引 DDL 不是忘了落地，而是**有意交给版本化迁移**——把有意为之的决定写清楚，才不会被后来者误读为遗漏。
