## 里程碑目标

上一轮企业级评估综合 **83/100**（企业级验收线 85）。行动计划给出"最快 85 路径 = T1 + T3 + T4"——三者**全部零外部依赖、本机可完整验证**。本轮把它们做完。

三件事分别对应三个不同的缺口：

1. **T1**：全项目**唯一"权重 30% + 缺口过半"**的项——买家侧体验完整性仅 **6/15**。`src/views/campus/` 原有 7 个页面**全是管理台风格**，买家旅程断在"看不到商品"这一步。
2. **T3**：AI 使用治理与边界仅 **8/12**，是 AI 维度**唯一未动的结构性缺口**，也是投入最低（纯文档）的一项。
3. **T4**：7 个项目**自己已如实披露、却一直未闭环**的遗留项——每一项都是"已知却未修"，对评分持续扣分。

## 关键决策与取舍

| 决策点 | 选择 | 备选方案 | 取舍理由 |
|---|---|---|---|
| 买家页面放在哪 | 新建 `mall/` 子目录（`index.vue` + `detail.vue`） | 复用 `product/index.vue` 加"买家模式"开关 | 管理台与买家视图的字段、操作、权限完全不同；用开关会让一个组件承担两套逻辑，且"管理员视角冒充买家"无法从菜单层面隔离 |
| 商城列表的筛选怎么做 | 服务端强制 `status=1`（只返回在售） | 前端拿到全部再过滤 | 前端过滤意味着已下架商品的标题/价格/库存仍会下发到浏览器，属不必要的信息暴露；且在售是业务语义，应在服务端收敛 |
| 详情页不可购买怎么拦 | 前端 `canBuy` / `buyBlockReason` 预拦 + 服务端强校验 | 只靠服务端返回错误 | 前端预拦是体验优化（避免点了才报错），**但不能替代服务端校验**——E2E 断言 16/17 已验证越权与非法流转被服务端拒绝 |
| 详情页路由如何注册 | 隐藏菜单 `menu_id=2009`（`visible='1'`） | 前端硬编码路由 | 若依路由由 `sys_menu` 驱动，未登记即无路由；但详情页需从卡片跳转进入，不应出现在侧边栏，隐藏菜单正是这个语义 |
| 卖家评价接口的 sellerId 从哪来 | **登录态**（`SecurityUtils.getUserId()`） | 前端传 `sellerId` | 前端可传即意味着可越权查他人评价；身份必须由服务端确定，与既有 `handler`、`sellerId` 的既有处理口径一致 |
| eslint warn 怎么治理 | 分两档：全仓 0 error + **自有目录 0 warning**（新增 `lint:strict`） | ① 全仓 0 warning；② 维持现状 | ① 不可行——161 条 warn 全在若依脚手架，改上游脚手架超出本项目范围且易引入回归；② 则新代码告警会混进噪声被长期忽略。分档把质量口径**钉在"我们写的代码"上** |
| AI 规范的核心立场 | "**'用了 AI'不是加分项，'能被验证的 AI 产出'才是**" | 写一份"AI 使用指南"罗列工具 | 任务书要的是"AI 辅助过程留痕"，但"留痕"本身不等于质量；规范必须落到**可验证性**（负向验证为强制动作、自述不算证据）才有意义 |
| 订单号并发怎么修 | 秒级时间戳 + 进程内 `AtomicInteger` 序列 | ① 雪花 ID；② 数据库序列 | ① 引入分布式 ID 生成器对单机演示系统过重；② 数据库序列增加一次往返。当前形态配 `uk_order_no` 唯一索引兜底已足够，**多实例边界如实写入注释** |

## 踩坑与解决

| 现象 | 根因 | 解决 |
|---|---|---|
| `mvn` 报 `command not found` | `mvn` 不在 PATH（本项目用随包 Maven，位于 `.tools/maven/bin`） | 显式 `export PATH="/d/.../.tools/maven/bin:$PATH"`；`JAVA_HOME` 指向 `jdk-17/jdk-17.0.20.1+1`（注意比预期多一层目录） |
| `npm run test:coverage` 直接报 `SAFE_DELETE_BULK_CONFIRM_REQUIRED` | vitest 启动时清理 `coverage/`（84 个文件）触发沙箱的**批量删除守卫**（阈值 50，`scope: turn`） | 改用 `npx vitest run --coverage --coverage.clean=false`，跳过清理步骤 |
| `npm run build:prod` 报同一守卫（`dist/static` 352 文件） | 同上——vite 在 `prepareOutDir` 阶段 `emptyDir` | 先把 `dist` 整体 `mv` 到备份目录，让 vite 无需删除既有产物；重建退出码 0 |
| 负向验证时改坏源码，但不确定用例是否真在断言 | —— | 还原旧 `genOrderNo` → 用例失败并报 `expected: <128> but was: <1>`（128 次并发下单只产出 1 个唯一订单号），证明用例确实在断言该行为；改回后全绿，`git diff` 确认无残留 |
