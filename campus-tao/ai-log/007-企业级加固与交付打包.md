# ai-log 007 · 企业级加固与交付打包

> 里程碑：M4（企业级能力加固）+ M5（交付打包） ｜ 主题：六维加固、fat-jar 原地重编译与交付验证 ｜ 记录方式：AI 辅助留痕

## 里程碑目标

在 M3 业务闭环之上完成企业级加固，并产出可交付的发行包：

- 从安全、一致性、可靠性、性能、工程化、运维六个维度加固，覆盖任务书「≥6 项企业级能力」要求；
- 在**交付机无 Maven、无本地 `~/.m2` 仓库**的条件下完成代码改动的重新编译与打包；
- 交付 Windows 绿色一体化发行包 `campus-tao-dist` 并完成端到端回归。

## 关键决策与取舍

| 决策点 | 选择 | 备选方案 | 取舍理由 |
|--------|------|----------|----------|
| 安全加固 | Spring Security + JWT；写接口 `@PreAuthorize`；身份取服务端 `SecurityUtils`；归属校验 | 仅前端菜单控制 | 后端二次校验，前端无法篡改归属人，越权返回 403 |
| 验证码策略 | 开关读自 `sys_config`，演示环境置 false | 硬编码/命令行参数 | 符合若依实际读取位置，演示便捷、生产可开 |
| 一致性加固 | 关键动作统一 `@Transactional(rollbackFor = Exception.class)` | 分散事务 | 库存与订单、退款与回补同事务，杜绝半完成 |
| 可靠性加固 | 乐观锁防超卖、支付幂等、账户原子扣款、状态机约束 | 仅应用层校验 | 数据库原子判断，并发下不超卖、不超扣 |
| 工程化加固 | 业务异常统一抛框架 `ServiceException`；另加全局异常处理器兜底未预期异常 | 直接抛堆栈 | 统一返回 code/msg，避免堆栈泄露 |
| 重编译方式 | **fat-jar 原地重编译** | 安装 Maven 重新构建 | 交付机无 Maven、无 `~/.m2`，原地重编译最可行 |
| 内层 jar 重打 | 使用保留目录条目的方式重打 `ruoyi-system` 内层 jar | 直接压缩文件列表 | 保留 zip 目录 entry 才能让 Spring Boot 正确解析嵌套 jar |

改动与验证要点：新增 `CampusGlobalExceptionHandler`（`@RestControllerAdvice`，兜底未预期的 `RuntimeException`）；业务异常统一由框架 `ServiceException` 处理；`payOrder` 增加幂等判断；JWT 密钥支持 `${JWT_SECRET:演示默认值}` 注入。

## 踩坑与解决

| 现象 | 根因 | 解决 |
|------|------|------|
| 交付机无 Maven 无法重新构建 | 无 Maven、无本地 `~/.m2` 仓库 | 采用 fat-jar 原地重编译：解包 `ruoyi-admin.jar` → 用 `javac` 增量编译改动类（classpath 指向 `BOOT-INF/lib` 下全部 jar）→ 重打 `ruoyi-system` 内层 jar → 替换进 fat jar |
| **启动报 `ISysConfigService` bean 缺失** | 重打内层 jar 时一度丢失了目录条目（zip 目录 entry），导致 Spring Boot 嵌套 jar 包资源解析失效、组件扫描扫不到类 | 补回目录条目后重新打包，启动成功。这是典型的嵌套 jar 打包陷阱 |
| E2E 单账号无法跑通 | `createOrder` 有「不能购买自己发布的商品」拦截；普通用户 `ry` 若无校园淘菜单权限会返回 403 | 必须先补菜单/角色 SQL，再将 E2E 由单账号改造为**双账号**（admin 卖家 / ry 买家） |
| 命令行改验证码开关无效 | 开关在数据库 `sys_config`，不在 yml | 直接更新 `sys_config.sys.account.captchaEnabled` |
| 上传路径失效 | 绝对路径 `D:/ruoyi` 不存在 | 改相对路径 `./uploadPath`，并刷新 jar 内 `application.yml` |
| 接口 500：`Name for argument of type [java.lang.Long] not specified` | 手工 `javac` 未带 `-parameters`，`@PathVariable`/`@RequestParam` 的参数名在 class 中丢失（Spring 6+ 不再从调试信息推断） | 一律加 `-parameters` 重编译，与 Maven 构建默认行为对齐 |
| **启动失败：`NoClassDefFoundError: com/ruoyi/common/core/controller/BaseController`** | 补丁 class 被 `jar uf` 写到了 fat jar **根目录** `com/ruoyi/...`，而 Spring Boot 只从 `BOOT-INF/classes/` 与 `BOOT-INF/lib/*.jar` 装载类，根目录条目不在类路径上，引发类加载紊乱 | 补丁类必须写入 `BOOT-INF/classes/`（该目录优先于 `BOOT-INF/lib` 下的模块 jar，从而覆盖模块 jar 中的同名类）；重打包改用 Python `zipfile` 逐条保留原 `compress_type`，确保嵌套 jar 仍为 STORED |
| 明文口令随仓库留痕 | DB 口令与 Druid 控制台口令硬编码在 `application-druid.yml` | 改为环境变量占位符（`${DB_PASSWORD:...}`、`${DRUID_LOGIN_PASSWORD:...}` 等）并同步刷新 jar 内该 yml；仓库尚无远程、历史仅一条提交，故重建根提交以清除明文 |
| **源码树无法 Maven 构建（164 处编译错误）** | 首次 `mvn clean package` 失败：`ruoyi-system/pom.xml` 从未声明编译期 `jakarta.validation` 依赖，而 campus DTO/Controller 与 `SysConfig`/`SysNotice`/`SysPost`/`SysUserServiceImpl` 都在用该 API | 补入 `spring-boot-starter-validation`（编译作用域），与运行时既有 Hibernate Validator 9.1.0 对齐；此前"能跑现成 jar"掩盖了该缺陷，说明**必须实际执行一次完整构建**才能暴露此类问题 |

3. 单元测试：JUnit 5 位于 `ruoyi-system/src/test/java/com/ruoyi/campus/`，两个测试类共 15 个用例全部通过（11 个 DTO 参数校验用例 + 4 个账户原子扣款 JDBC 用例）。可在无 Maven 环境下用 JUnit Platform Console Standalone 运行；接入 Maven 后 `mvn test` 可执行。

4. 健康检查：若依原生未引入 Actuator，存活探针以 `curl http://localhost:8080/captchaImage` 返回 200 为准；启动期打印端口与内嵌 Redis 状态。

## 补充加固（P0 / P1 收尾）

在初版加固之后，针对评审发现的缺口做了第二轮加固，均为「先改源码 → 用 JDK 17 重编译 → 注入 `BOOT-INF/classes/` → 重启验证」的同一流程：

| 项目 | 改动 | 验证 |
|------|------|------|
| 横向越权（IDOR） | 购物车改数量/勾选/删除校验归属；商品修改/上下架/删除校验「卖家本人或管理员」；商品编辑改字段白名单，不再接收 `sellerId/sellerName` | 双账号实测：ry 改他人购物车被拒（500），admin 购物车数量不变；夹带 `sellerId=999` 编辑商品后落库仍为 1；`GET /campus/product/{id}` 200 |
| 审核归属防伪造 | 审核人改取 `SecurityUtils.getUsername()`；`CampusAftersaleAuditDTO` 移除 `handler`；前端不再传该值 | E2E 新增断言：传 `handler=forged-hacker` → 库中仍为 `admin`，全链路 `RESULT: ALL_PASS` |
| 密钥外部化 | DB 账号口令、Druid 控制台口令改环境变量占位符，源码内无明文 | 重启后 Druid 数据源初始化成功、接口 200（默认值回退生效），jar 内该条目与源码哈希一致 |
| 版本控制 | `git init -b main`，`.gitignore` 排除内置 JDK/MySQL、`node_modules`、`target`、`uploadPath`、日志；重建根提交清除明文口令 | 仓库 711 个文件入库，`git grep` 校验 HEAD 无明文口令 |
| 交付包卫生 | 删除 fat jar 解包残留（`BOOT-INF`/`META-INF`/`org`，98.9MB/175 文件）与 `mysql_test.log` | 外层目录仅剩交付根 |
| C2C 卖方权限 | 为角色 2（学生）补授 `campus:product:add/edit/remove`（2100~2102），并同步写回交付 SQL `sql/campus_tao_full.sql` 的 `sys_role_menu` 插入行 | 重新登录后 ry 发布商品 200、卖家强制为本人（伪造 `sellerId=99` 被忽略）；售后审核仍 403；e2e 全链路 `RESULT: ALL_PASS` |
| Maven 纯净重建 | 修复 `ruoyi-system/pom.xml` 缺失的编译期 `jakarta.validation` 依赖（补入 `spring-boot-starter-validation`，移除冗余 test 作用域 `hibernate-validator`）；用 Maven 3.9.9 + JDK 17 执行 `mvn -DskipTests clean package` | BUILD SUCCESS；`mvn test` 15/15 全绿；新 jar 外层**零**手工注入 class、改动类进内层 `BOOT-INF/lib/ruoyi-system-3.9.2.jar`；jar 内配置为外部化占位符；以新 jar 启动后 E2E `RESULT: ALL_PASS` |

> 说明（构建链路沿革）：P0/P1 阶段的改动曾以 `javac -parameters` 重编译后注入 `BOOT-INF/classes/` 的方式落进 jar，运行时优先于 `BOOT-INF/lib/ruoyi-system-3.9.2.jar` 中的同名类。该方式只是**交付机上无 Maven 时的过渡手段**，现已由 Maven 纯净重建取代：发行 jar 完全由源码构建产出，外层无任何手工 class，构建过程可重现。
