# ai-log 005 · 支付账户与售后模块

> 里程碑：M3（业务闭环 · 分块三） ｜ 主题：支付账户、售后与评价模块后端实现 ｜ 记录方式：AI 辅助留痕

## 里程碑目标

补齐闭环中与资金和售后服务相关的能力：

- 支付账户域：沙箱余额展示、充值、支付扣款、退款回退；
- 订单支付：支付幂等与状态机约束；
- 售后域：申请售后、管理员审核（通过则退款并回补库存）；
- 评价域：订单完成后提交评价。

## 关键决策与取舍

| 决策点 | 选择 | 备选方案 | 取舍理由 |
|--------|------|----------|----------|
| 支付方式 | 沙箱余额模拟 | 对接第三方支付 | 符合实验「模拟支付」要求，聚焦闭环 |
| 账户扣款 | 原子化 `UPDATE campus_account SET balance=balance-? WHERE user_id=? AND balance>=?` | 先查余额再更新 | 余额不足时影响行数为 0，天然防并发超扣 |
| 支付幂等 | 对已付款订单重复支付直接返回成功 | 每次重新扣款 | 防网络重试导致的重复扣款 |
| 支付状态约束 | 仅待付款订单可支付 | 无约束 | 状态机强约束，非法跃迁直接拒绝 |
| 售后审核 | 审核通过时，退款（余额回退）与库存回补同事务 | 分两步异步处理 | 保证资金与库存双向一致，杜绝半完成状态 |
| 审核权限 | `campus:aftersale:edit` 仅授予管理员 | 买家也能改售后状态 | 防止自审自批；普通买家调用返回 403 |
| 账户行创建 | 首次充值时自动创建账户行 | 预置账户数据 | 降低演示前置步骤，账户随首次使用生成 |

相关权限字符串：`campus:account:balance / edit`、`campus:aftersale:list / add / edit`、`campus:review:add`。

## 踩坑与解决

| 现象 | 根因 | 解决 |
|------|------|------|
| 普通买家 `ry` 调用校园淘接口返回 403 | `ry` 角色未授予校园淘菜单/按钮权限 | 先补齐菜单/角色授权 SQL（`ry` 授予 2001、2003、2004、2005、2006 及 2106-2112、2114），再跑 E2E |
| 售后审核可能被买家自助通过 | 审核接口权限未收敛 | 审核按钮 2113 权限仅授予 admin，`ry` 调用返回 403 |
| 重复支付导致重复扣款 | 支付未做幂等 | 已付款订单重复支付直接返回成功 |
| 并发支付可能超扣 | 非原子扣款 | 改用带 `balance>=?` 条件的原子 UPDATE |
| 退款后库存未回补 | 退款与回补未同事务 | 两者放入同一 `@Transactional(rollbackFor = Exception.class)` |

## 验证证据

1. 沙箱充值（E2E 步骤 2）：`ry` 充值 500 → 成功（首次自动创建账户行）。

2. 支付扣款（E2E 步骤 6）：

```
ry 支付 → 支付成功
PASS 支付扣款金额正确：60
沙箱余额 500 → 440
```

3. 评价（E2E 步骤 9）：`ry 评价 → 评价成功`。

4. 售后退款（E2E 步骤 10~11）：

```
ry 申请售后（退货退款）→ 申请已提交
admin 审核通过 → 审核完成
PASS 余额回滚一致：500.0 == 500.0        （余额 440 → 500）
PASS 库存回滚一致：5                     （库存 3 → 5 回补）
```

5. 权限收敛（E2E 专项）：

```
PASS 权限收敛：ry 越权调用售后审核返回 403（防自审自批）
```

6. 账户原子扣款单元测试（4 个 JDBC 用例全部通过）：

```
余额充足 → 扣款成功
余额不足 → 拒绝扣款，余额不变
重复退款 → 累加
事务回滚 → 撤销
```
