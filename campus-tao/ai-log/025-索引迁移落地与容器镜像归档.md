# 025 · 收口 v1.0.21 的两项「未纳入」：索引迁移落地 + 容器镜像归档

## 1. 目标与结论
v1.0.21 的 CHANGELOG 明确记录了两项未完成项：

1. **候选索引 DDL 未落地交付库**——性能报告里的 4 条复合索引只存在于 `perf/idx-candidate.sql`，交付库并未受益；
2. **容器镜像未归档**——CI 的 `docker` job 只验证「能构建、能起栈」，未推镜像仓库、无 digest。

本轮把两项收口。**结论**：`V4__product_order_indexes.sql` + `U4` 已纳入版本化迁移并在本地完成全链路验证；`release-image.yml` 在 `v*` tag 上推送 GHCR 并产出 digest，随 Release 归档。

## 2. 关键实现

### 2.1 V4 索引迁移（4 条复合索引）
- 落地索引：`campus_product.idx_status_time (status,create_time)`、`idx_seller_time (seller_id,create_time)`、`idx_category_status_time (category_id,status,create_time)`、`campus_order.idx_user_time (user_id,create_time)`。
- 设计原则与性能实验一致：**过滤列与 `create_time` 编进同一索引**，消除 `Using filesort` 并转为 `Using index`。
- **幂等实现**：MySQL 8.0 不支持 `CREATE INDEX IF NOT EXISTS`，故先查 `information_schema.STATISTICS`，命中则 `DO 0`、未命中则 `PREPARE/EXECUTE` 执行 `ALTER TABLE`。`U4` 用同样的守卫反向处理。
- 迁移验证链 `db/tools/verify_flyway.sh` 由 V3 扩到 V4：版本断言 `1,2,3,4`、表数 47，并在「空库迁移 / 回滚后 / 重放后」三处断言 4 条索引。
- **断言的坑**：`campus_search_history` 也有一个同名 `idx_user_time`，裸判会假通过；断言必须带 `table_name` 限定与 `seq_in_index=1`。
- `sql/campus_tao_full.sql` 同步补入 4 条索引，使**存量库升级（V4）**与**全量脚本新建**两条路径口径一致——否则新建库反而没有索引。

### 2.2 容器镜像归档（GHCR + digest）
- 新增 `.github/workflows/release-image.yml`，与 `ci.yml` 的 `docker` job **职责分离**：CI 只验证可构建可起栈，新 workflow 只负责发布。
- 矩阵构建 `campus-tao-backend` 与 `campus-tao-ui`，推送 `ghcr.io/<owner>/<image>:<version>` 与 `:latest`，`build-push-action` 输出 digest。
- `permissions` 显式声明 `contents: write` + `packages: write`，不依赖默认权限。
- digest 双份留痕：Actions artifact + Release 资产 `campus-tao-images-v<version>.txt`（record job 等待 Release 创建，最多约 20 分钟）。

### 2.3 镜像漏洞扫描（Trivy + 报告归档）
- 新增 `scan` job：从 `images` 的 artifact 里解析 **digest**，按 `ghcr.io/<owner>/<image>@sha256:...` 扫描，而不是按 tag——tag 会被下一次构建覆盖，按 tag 扫出来的证据可能对不上发布物。
- 口径：`severity=CRITICAL,HIGH` + `ignore-unfixed=true` + `scanners=vuln`；**CRITICAL 数量大于 0 即失败**，HIGH 只记录。忽略无修复版本是刻意的：基础镜像里上游尚未修复的漏洞无法靠本项目解决，不该让发布永久卡红。
- `trivy-action` 的 `exit-code` 设为 `0`，门禁由自己的 `jq` 统计决定——这样即使失败，JSON 也一定落盘，artifact 与 Release 才有证据可看。
- `record` 改为 `needs: [images, scan]` + `always()`：**扫描失败时 digest 与报告照样挂到 Release**，红叉本身就是结论，不能因为失败就丢失证据。
- 归档：Actions artifact `trivy-<image>`（JSON + 摘要），Release 资产 `campus-tao-security-scan-v<version>.md` + `trivy-<image>-v<version>.json`。

### 2.4 顺带修复的漂移
- `docker-compose.yml` 两处 `APP_VERSION:-1.0.17` → `1.0.22`；「V1/V2 迁移」注释 → 「V1~V4」。
- `application.yml` 的 `info.app.version` 发布前先升到 `1.0.22`（v1.0.21 曾因先打 tag 后改版本而被迫移动 tag）。

## 3. 首次实跑抓到的真实缺陷
**`record` job 空转到超时**：该 job 只 `download-artifact`，**没有 `checkout` 仓库**，因此 `gh` 没有本地仓库上下文，
`gh release view v1.0.22` 以「not a git repository」失败；错误又被 `2>/dev/null` 吞掉，
表现成「Release 迟迟未创建」的空转，直到 20 分钟循环耗尽才失败（本次由人工取消）。
修复：两条 `gh` 命令显式加 `--repo "$GITHUB_REPOSITORY"`。
**本地 YAML 语法检查、CI 的六个常规 job 都不会暴露此类缺陷——只有真跑一次 tag 才发现。**
修复后移动 tag 到修复提交重跑（run `39029813856`）：`镜像 campus-tao-backend`、`镜像 campus-tao-ui`、`汇总 digest 并挂到 Release` 三个 job 均 success，
Release 第 5 件资产 `campus-tao-images-v1.0.22.txt` 已挂上。

### 3.1 Trivy 扫描 job 的两次失败（run `39035102116` / `39035297622`）
- **action 版本号写错**：`aquasecurity/trivy-action@0.36.0` 在 `Set up job` 阶段就失败——
  `Unable to resolve action ... unable to find version 0.36.0`。该仓库的 release tag 带 `v` 前缀（`v0.36.0`），
  与很多 action 只发裸版本号的习惯不同；本地 YAML 语法检查对此完全无感。
- **前端镜像扫出 2 个可修复 CRITICAL**：`libcrypto3` / `libssl3 3.3.3-r0`（CVE-2026-31789，修复版本 `3.3.7-r0`），HIGH 41 个。
  根因是 `nginx:1.27-alpine` 基于 **Alpine 3.20（2026-04 已 EOL）**，上游安全修复停更，镜像里的 openssl 永远等不到新包。
  把基础镜像升到 `nginx:1.30.6-alpine` 后复扫：CRITICAL 0 / HIGH 0。
- 这两次失败恰好说明了扫描门禁的价值：**「镜像能构建、能起栈」与「镜像没有已知可修复漏洞」是两件事**，前者 CI 早已覆盖，后者只有真扫才知道。
