# 027 · C2C 卖家收款码直付（P0-1 过渡落地）

## 1. 目标与结论
用户提出用个人微信收款码打通真实支付。评估结论：**平台收款码代收不可行**（违反微信个人
收款码经营性使用规范 + 无牌照平台代收代付构成「二清」红线 + 个人码无回调 API 无法自动
确认），改走 **C2C 卖家收款码直付**：每个卖家上传本人收款码，买家扫码直接付给卖家本人，
平台全程不经手资金、只做状态撮合。个人间闲置转让用个人码收款合法，无二清问题。

**结论**：V8 迁移落地（状态 7 待卖家确认收款 + 收款码表）；后端 13 例新测全绿、
全量后端 336 例 / 前端 220 例全绿；verify_flyway.sh 扩至 V8 全通过（迁移 → 回滚 → 重放）；
前后端生产构建通过。评估报告登记的 compose APP_VERSION 漂移（1.0.22）顺手对齐 1.0.26。

## 2. 关键实现

### 2.1 状态机与数据
- 新状态 **7 待卖家确认收款**：0 --买家扫码付款+我已付款--> 7 --卖家确认已收款--> 1（写 pay_time）。
  状态 7 与 0 一样占库存，超时自动取消扫描 SQL 同步纳入（status in (0,7)，与 V7 的
  idx_status_time 索引兼容）。
- V8 迁移：campus_order 加 `pay_type`（0 沙箱 / 1 直付）、`seller_id`、`pay_proof_url`；
  新表 `campus_user_pay_qr`（一人一码主键）。幂等判存写法同 V7；U8 回滚 + full.sql 同步。
- **full.sql 的坑**：其 `INSERT INTO campus_order VALUES` 是全列无列名清单，DDL 加列后
  列数不匹配直接炸导入——INSERT 补列名清单后新列走默认值。

### 2.2 三道硬校验与原子状态推进
- 跨卖家订单（购物车混购多个卖家的商品）拒绝直付——一个收款码只对应一个人；
- 卖家未上传收款码明确拒绝，不展示空图；
- `markAwaitSellerConfirm`（status=0 → 7）与 `confirmPayIfAwaitConfirm`（7 → 1）均为
  带状态条件的原子 UPDATE，与沙箱支付/取消/超时取消并发时只有一方生效，影响 0 行显式报错。

### 2.3 前端交互
- 支付账户页「我的收款码」管理卡片（ImageUpload 上传 + 知情提示）；
- 订单页「扫码直付」弹窗：展示卖家收款码 + 应付金额 + 可选付款截图 + 我已付款；
- 卖家视角：订单列表对卖家可见自己卖出的订单（Filter_Where 扩展 `or seller_id=#{userId}`），
  行内「我卖出的」标记 +「确认已收款」按钮；详情权限同步放行卖家；
- 取消文案按状态区分：直付订单如实告知「款项已直接付给卖家，退款需线下协商，平台仅记录状态」。

## 4. 遗留与边界（如实登记）
- 平台无资金担保能力，退款依赖买卖双方线下协商（前端弹窗知情提示 + 通知文案如实）；

- 商户号到位后应以微信支付 JSAPI/Native 替换本通道，pay_type 字段即为切换预留；
