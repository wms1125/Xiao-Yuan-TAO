# ai-log 011 · 演示数据重做与真实感数据集

> 里程碑：M9（交付数据质量） ｜ 主题：真实校园二手场景数据集、生成器脚本化改造、图片方案降级 ｜ 记录方式：AI 辅助留痕

## 里程碑目标

交付包里的演示数据是早期联调阶段随手造的："测试二手显示器886373"、"限量1件测试"、评价一律"东西很好，好评"、收货人一律"张三"、购物车数量一律 2。作为**功能演示**它够用（能跑通链路），但作为**交付物**它不合格：

- 打开商品列表一眼就能看出是机器生成的数据，与"校园二手交易平台"的人物设定冲突；
- 评价、售后、物流、通知这些"周边数据"与商品无任何语义关联，无法体现业务闭环的完整度；
- 部分数据本身**不合业务逻辑**（用户把自己发布的商品加进了购物车、售罄商品仍显示上架、购物车数量超过库存）。

本次目标：把这套数据换成**贴合真实校园二手交易场景**的数据集，并且**脚本化**——保证重跑 `1-初始化数据库.bat` 得到的是同一套数据，而不是靠手工往库里补。

## 关键决策与取舍

| 决策点 | 选择 | 备选方案 | 取舍理由 |
|--------|------|----------|----------|
| 数据集的载体 | 写 `tools/gen-seed-data.py` 生成器，直接**改写 `sql/campus_tao_full.sql` 的数据块** | ① 手写 INSERT 贴进全量脚本；② 另写 `seed.sql` 让初始化脚本多导一次 | 全量脚本是交付包的**唯一建库源**（同学只跑 `1-初始化数据库.bat`），多一个 `seed.sql` 就多一个"忘了导"的失败点；手写 49 件商品的 INSERT 无法保证一致性（总价、库存、时间链）。生成器把"数据"与"一致性推导"放在一处，改一处即可重放 |
| 商品数据规模 | 10 分类 / 49 商品 / 24 订单 / 33 订单项 / 20 评价 / 4 售后 / 12 购物车 / 14 通知 / 16 轨迹 / 8 外呼留痕 / 8 账户 | 更小（几十条凑数）或更大（几百条） | 49 件商品刚好让**每个分类都有货**且列表分页（10/页）需要翻 5 页；24 笔订单刚好覆盖**七种状态**且每状态 2~5 笔。再大只会让审阅成本上升、演示价值不变 |
| 商品图片来源 | **随包交付 11 张品类实拍图**，`images` 存 `/campus-img/<品类>.jpg` | ① 在线文生图 URL；② 全部留空（前端渲染"无图"占位） | 见下方"踩坑 1"：在线文生图接口实测**恒返回同一张占位图**，方案不可用；留空则列表 49 行全是灰色"无图"框，观感劣于有图。品类实拍图（每类 1 张、同类商品共用）在"够真实"与"体积可控"之间取平衡 |
| 商品卖家的来源 | 新增 **6 名学生账号**（`liyutong`/`wanghao`/`zhaomin`/`chenxinyi`/`zhoukai`/`liuzhiyuan`，角色 2，密码统一 `admin123`） | 全部挂在 admin / ry 名下 | 校园二手的本质是 **C2C**：商品应来自"不同同学"。只用 admin/ry 会让"卖家"列清一色两个名字，且无法体现"学生也能发布商品"这条已开放的权限（`sys_role_menu` 已给角色 2 补授 2100~2102） |
| 商品上架时间 | 在 `2026-08-18 ~ 2026-09-05` 区间内**确定性打散**（`(i*7)%19` 天 + 小时/分钟扰动） | 随索引单调递增（每件 +10 小时） | 列表按 `create_time desc` 排序，单调递增会让**首页整页扎堆在最后录入的分类**（票券卡类/美妆个护），看起来像"这个平台只有电影券"。打散后每个分类都能上首页；同时必须**早于最早订单**（2026-09-08），否则出现"先下单后上架" |
| 售罄商品的上下架状态 | 剩余库存为 0 → `status=0`（下架） | 保持 `status=1`（上架） | 上架却买不到，是**可被当场戳穿的业务逻辑错误**（点"加购"才发现库存 0）。19 件售罄商品统一下架，列表里"在售"的都能买 |
| 待付款订单的创建时间 | 表达式 `DATE_ADD(UTC_TIMESTAMP(), INTERVAL 8 HOUR)`（导入即当前时刻），订单号同步用 `CONCAT(DATE_FORMAT(...))` 生成 | 写死一个固定时间戳（如 `2026-10-15 08:45:00`） | 见下方"踩坑 2"：写死的"待付款"订单会在服务启动 30 分钟后被**超时自动取消任务**静默改写，数据集不可复现 |
| 成色字段口径 | 与前端一致：`1=全新 / 2=几乎全新 / 3=轻微使用 / 4=明显使用 / 5=二手老旧` | 沿用 DDL 注释里的"成色(1-5,5=最新)" | 前端 `conditionOptions`/`conditionText` 是用户实际看到的口径，**以 UI 为准**；DDL 注释是过时描述（已在数据注释中写明口径来源） |
| 金额与库存的一致性 | 由生成器**推导**：订单 `total_amount` = Σ(order_item.subtotal)；商品 `stock` = 初始库存 − 未回补订单的占用数 | 手填一个"看起来合理"的数 | 手填必然出现 `total_amount ≠ Σsubtotal` 这类**一查就崩**的问题；推导 + 落库前自检把这类错误挡在脚本之外 |

## 踩坑与解决

| 现象 | 根因 | 解决 |
|------|------|------|
| 选定的"在线文生图 URL"方案产不出可用图片 | 实测 `https://trae-api-cn.mchost.guru/api/ide/v1/text_to_image` 对**任意 prompt / 任意 image_size** 恒返回同一张 `176626` 字节图片（MD5 恒为 `19A0B822EDB11957055E4588C2159058`），下载后内容是「The image is generating… Please refresh page to preview.」的灰色占位图 | 改用 `GenerateImage` 工具**本地生成 11 张品类实拍图**放入 `campus-tao-ui/public/campus-img/`，`images` 改存站点根路径（前端 `firstImage()` 直接取首段作 `src`，无需拼 base API）。方案降级如实记入 CHANGELOG 的"修复"节 |
| 库里"待付款"订单在服务启动后**静默变成"已取消"** | `CampusOrderTask` 每 30 分钟按 `status=0 且 create_time < now-30min` 自动取消并回补库存。静态写死的"待付款"订单只要早于当前时刻 30 分钟，**必然**被改写 | 该订单 `create_time` 改为导入时刻表达式；订单号同步由 `CONCAT` 生成（保证单号与时间一致）。数据集从此**可复现**：无论何时重跑初始化脚本，它都落在支付窗口内。（导入 30 分钟后它仍会按业务规则自然转为"已取消"并回补库存——这是**功能本身的正确行为**，不是数据缺陷；需要长期展示"待付款"当场下一单即可。） |
| 生成的订单号/时间比真实时间晚 8 小时 | 全量脚本由 mysqldump 导出，脚本头部有 `/*!40103 SET TIME_ZONE='+00:00' */`——**脚本内的 `NOW()` 是 UTC**，而运行期 JDBC 走 `serverTimezone=GMT+8` | 统一用 `DATE_ADD(UTC_TIMESTAMP(), INTERVAL 8 HOUR)` 表达"GMT+8 的当前墙上时间"，与 JDBC 读取口径一致（实测导入后该订单 `create_time` 距当前 0 分钟） |
| 生成器里 `DATE_FORMAT` 的 `%` 被写成 `%%` 后反而报错 | 该字符串经 Python 的 `%` 格式化拼接，第一版按"双重转义"处理（`%%Y%%m`），结果 SQL 里出现 `%%Y` | 改为先把表达式预拼好再嵌入（不再经过 `%` 格式化），SQL 中为单 `%` |
| 商品上架时间集中在个别分类 | 见"关键决策"：首版用 `(i-1)*10 小时` 单调递增，首页按时间倒序后全是最后录入的分类 | 改为区间内确定性打散，并在自检中加入"商品上架时间 < 最早订单创建时间"断言 |
| 购物车数据不合业务逻辑 | 首版购物车出现三类问题：① 用户加购**自己发布**的商品；② 加购**已售罄（下架）**商品；③ `quantity`（2）**超过剩余库存**（1） | 逐条改正，并在生成器自检中增加三条对应断言——**让错误在脚本阶段就暴露，而不是留到演示时被追问** |
| 生成器重复执行会追加出重复学生账号 | `campus_*` 表是"整块替换"（天然幂等），但 `sys_user`/`sys_user_role` 是**追加**到既有 INSERT 之后，第二次执行会把 6 名学生再加一遍（导入时主键冲突） | `append_rows()` 改为**按行首 ID 去重**，重复执行不再追加已有账号；实测连续执行两次，脚本 MD5 完全一致（`111399 -> 111399` 字符） |

## 设计落地

**生成器**（`campus-tao/tools/gen-seed-data.py`，约 620 行）

| 部分 | 内容 |
|------|------|
| 常量/工具 | `q()` 单引号转义、`ts()` 14 位时间戳、`prod_time()` 上架时间打散、`now_expr()` GMT+8 当前时刻表达式 |
| 图片映射 | `IMG_FILES` 商品 ID → 品类图 key；`img_path()` 返回 `/campus-img/<key>.jpg` |
| 数据集 | `CATEGORIES`(10) / `STUDENTS`(6) / `PRODUCTS`(49) / `BUYER_INFO` / `ORDERS`(24) / `REVIEWS`(20) / `AFTERSALES`(4) / `CARTS`(12) / `NOTICES`(14) / `NOTIFY_LOGS` / `TRACE_KEYS` / `BALANCES` |
| 推导逻辑 | 订单总额 = Σ 明细小计；商品剩余库存 = 初始库存 − 未回补订单占用；售罄自动下架 |
| 回写 | `patch()` 用正则整体替换全量脚本中每张表的 `LOCK TABLES … DISABLE KEYS` 与 `ENABLE KEYS` 之间的数据块；`append_rows()` 按 ID 去重追加学生账号与角色 |
| 自检 | 条数统计、订单总额一致性、订单"买家≠卖家"、商品上架时间早于最早订单、售罄商品上架数、购物车三类越界 |

**数据特征**（与真实场景对齐的具体做法）

- **商品标题**用真实书名/型号：`《操作系统概念》第9版（恐龙书）`、`Kindle Paperwhite 4 8G 含原装皮套`、`宿舍小电锅 1.2L（可煮面/粥）`、`捷安特 ATX 山地车 27 速`。
- **商品描述**带真实瑕疵话术：`书角有轻微卷边，内页无笔记，赠全套课后答案 PDF`、`屏幕无划痕，电池健康 91%，配原装充电器`。
- **订单备注**像学生本人写的：`书有几页笔记，介意勿拍`、`先下单占着，明天发生活费就付，麻烦帮我留一下`。
- **收货信息**是校园地址：`东区6号宿舍楼302室（可放菜鸟驿站）`、`西区9号宿舍楼412室`。
- **评价文案**呼应具体商品：`书基本全新，笔记做得很整齐`。
- **售后**覆盖三种审核结果（待处理/已通过/已驳回），且驳回理由写在通知里。
- **通知/轨迹/外呼留痕**与订单、售后单**用真实业务号关联**（`O8`、`ASxxx`），不是孤立数据。

## 验证证据

1. **生成器自检**（每次改写后自动打印）：分类 10 / 商品 49 / 订单 24 / 订单项 33 / 评价 20 / 售后 4 / 轨迹 16 / 外呼留痕 8 / 站内通知 14，学生账号 6；售罄下架 19 件；上架时间 `2026-08-18 16:46:00 ~ 2026-09-05 20:16:00`；**一致性检查：全部通过**。

2. **幂等性**：连续执行生成器两次，`campus_tao_full.sql` 的 MD5 完全一致（`111399 -> 111399` 字符），不会重复追加学生账号。

3. **库内复核**（导入 `campus_tao` 后 SQL 抽查）：13 张表计数与生成器一致；`total_amount` 与 `Σsubtotal` 不一致 **0** 笔；订单"买家=卖家" **0** 笔；购物车自有/已下架/超库存 各 **0** 条；`stock=0 且 status=1` **0** 件；49 件商品 `images` 全部为 `/campus-img/` 前缀；待付款订单 `create_time` 距当前 **0 分钟**。

4. **接口抽查**：商品列表 49 条（分类筛选、关键词搜索正常）；订单 24 笔七态齐全；学生账号 `zhoukai` 站内通知 3 条未读（含"订单待支付提醒"）；售后 4 单；学生账号发布商品成功且卖家被服务端强制改写为本人。

5. **前端实测**（浏览器，`/campus/product`、`/campus/order`）：第 1 页 10 行缩略图**全部渲染为品类实拍图**、无"无图"占位；订单页 24 行、七种状态标签齐全；静态资源 `/campus-img/books.jpg` 返回 `200 image/jpeg`（232 KB）。

6. **回归**：`e2e_business.py` `RESULT: ALL_PASS`（种子数据与 e2e 双账号流程无冲突——列表按发布时间倒序故新发布商品必在首页、购物车结算用显式 `cartIds`、C2C 用例以时间戳标题区分）；`verify.bat` 离线 5 步 `ALL PASS`（后端单测 23/23、前端单测 44/44）。回归后重新导入全量脚本，交付库回到本报告所述基线。

7. **交付语义变更**：v1.0.5 起"交付库为空库（仅 1 条分类主数据）"的约定在本版**作废**——交付库现在自带真实感数据集，`同学运行指南.md` 第四节新增"开箱即用的演示数据"与演示账号表。
