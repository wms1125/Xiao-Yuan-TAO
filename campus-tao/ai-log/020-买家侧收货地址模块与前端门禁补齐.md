## 2. 关键实现

### 2.1 归属校验做两层，不是一层

`CampusAddressMapper` 的删除 SQL 直接带 `user_id` 条件：

```java
int deleteCampusAddressById(@Param("addressId") Long addressId, @Param("userId") Long userId);
```

服务层另有 `requireOwned(addressId, userId)`，拿不到就抛 `收货地址不存在或无权操作`。两层各自独立生效——**SQL 层挡住的是"绕过服务层直接写库"的路径，服务层挡的是"忘写条件"**。所有 7 个接口的 `userId` 一律取自 `SecurityUtils.getUserId()`，不接受任何前端传参。

### 2.2 默认地址的互斥用"先清后设"

```java
if (dto.getIsDefault() != null && dto.getIsDefault() == 1) {
    addressMapper.clearDefaultByUser(userId);   // 先清该用户全部默认位
    address.setIsDefault(1);
}
```

首条地址强制置默认（`addressList.isEmpty()` 时直接置 1），保证"用户永远有一条默认地址"这个业务不变量。上限 `MAX_ADDRESSES_PER_USER = 20`，前后端常量各写一份并互相注明要保持一致。

### 2.3 下单时地址簿条目覆盖手填字段，并冻结快照

`CampusOrderServiceImpl` 的签名从"手填收货人/电话/地址"改为"额外带一个 `addressId`"：

```java
String snapshot = address;
if (addressId != null) {
    CampusAddress chosen = addressService.requireOwned(addressId, userId);
    receiverName = chosen.getReceiver();
    receiverPhone = chosen.getPhone();
    address = chosen.fullAddress();
    snapshot = chosen.getReceiver() + " " + chosen.getPhone() + " " + chosen.fullAddress();
}
```

**地址簿条目是权威来源**：用户同时手填了 `张三 / 13800000000 / 东校区1号楼101` 并选了地址簿里的 `李四 / 13900000000 / 西校区2号楼202`，入库结果以地址簿为准（见 §4.2 的 DB 直查）。`address_snapshot` 把下单那一刻的收货信息冻结下来，后续用户改地址簿不会追溯改写历史订单。

### 2.4 MySQL `DEFAULT` 的一个坑：NULL ≠ 省略

`address_snapshot varchar(400) NOT NULL DEFAULT ''`，但 MyBatis 传显式 `NULL` 时 **MySQL 的 `DEFAULT` 不生效**（它只在"整列被省略"时套用），于是 7 个订单相关用例报 `Column 'address_snapshot' cannot be null`。mapper 改成：

```xml
COALESCE(#{addressSnapshot,jdbcType=VARCHAR}, '')
```

并补 `jdbcType` —— 不声明类型时 MyBatis 对 `null` 会推断不出 JDBC 类型而报 `JdbcType OTHER`。

## 3. 本轮抓到的三个真实缺陷（都是"自述不算证据"的正面例子）

三个缺陷都不是靠读代码看出来的，是靠测试跑出来的。全部有失败证据。

### 3.1 取消确认框产生未处理的 Promise 拒绝

原写法：

```js
await ElMessageBox.confirm(...).catch(() => { throw new Error('cancel') })
try { await setDefaultAddress(...) } catch { }
```

`.catch()` 里 `throw` 会把取消异常重新抛出 `handleSetDefault` 这个 async 函数——而模板里 `@click="handleSetDefault(row)"` 没有 `await`，于是变成**未处理的 Promise 拒绝**。`try/catch` 只包住了接口调用，包不住取消。

测试输出（修复前）：

```
⎯⎯⎯⎯ Unhandled Rejection ⎯⎯⎯⎯
Error: cancel
 ❯ src/views/campus/address/index.vue:247:11
 ❯ Proxy.handleSetDefault src/views/campus/address/index.vue:244:3
Vitest caught 2 unhandled errors during the test run.
```

修复：把确认与请求统一包进一个 `try`，取消与接口失败一并被 `catch` 吞掉（取消不提示，失败由请求拦截器统一提示）。修复后 `Errors 0`。

### 3.2 `form` 裸解构导致输入框永远为空 —— 最严重的一个

原写法（也是若依脚手架 `system/user/index.vue` 的写法被我用错了）：

```js
const data = reactive({ form: {} })
const { form } = data          // ← 裸解构，拿到的是旧对象的引用
...
form.value = { receiver: '王五', ... }   // 整体替换对象
```

模板里 `v-model="form.receiver"` 绑的是解构出来的那个**旧引用**。`reset()` / `handleUpdate()` 会整体替换 `form.value`，替换后模板仍指向旧对象 —— **输入框永远是空的，`prop="receiver"` 的校验目标也永远 undefined**。

若依正解是 `toRefs`：`const { form } = toRefs(data)`，此时 `form` 是 ref，`form.value = {...}` 会同步回 `data.form`，模板自动解包后绑定正确。

测试输出（修复前）：

```
AssertionError: expected '' to be '王五'
 ❯ tests/unit/views.campus.address.test.js:155:37
```

**注意这个缺陷的特征**：接口层完全正常（`updateAddress` 被正确调用、`addressId` 也传对了），只有 UI 层静默失效。如果只看"接口测过了"就认为功能可用，这个 bug 会直接漏到生产。

### 3.3 测试替身库本身的三处不保真

- `el-dialog` 替身**不渲染 `title`** —— 而新增/修改两种弹窗靠标题区分，断言失败才发现；
- `el-form` 替身没暴露 `clearValidate` —— 页面 `reset()` 里经 `formRef` 调用，替身缺方法会在 `nextTick` 里抛 `TypeError`；
- `el-input` 替身把 `placeholder` 声明为 prop 却**从不渲染** —— 声明了就当消费掉，不进 `attrs`，于是属性断言拿不到值。

替身的原则是"结构保真、能力最小"。替身自己丢行为，测出来的绿是假的。
