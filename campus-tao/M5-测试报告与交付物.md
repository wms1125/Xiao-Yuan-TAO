## 二、接口/集成测试执行结果（E2E，RESULT = ALL_PASS）
执行 `python e2e_business.py`，采用**双账号**流程（admin 作卖家、ry 作买家），覆盖全链路与越权/超卖专项：

1. 双账号登录（admin、ry）→ 均返回 token
2. ry 沙箱充值 500 → 成功（首次自动创建账户行）
3. admin 发布商品（**故意伪造 sellerId=99**）→ 服务端强制改写为登录用户 1
4. ry 加入购物车（数量 2）→ 成功
5. ry 下单（显式购物车项）→ `下单成功`，订单号 `CT...`
6. ry 支付 → `支付成功`，沙箱余额 **500 → 440**（扣 60）
7. admin 发货 → `已发货`
8. ry 确认收货 → `已确认收货`
9. ry 评价 → `评价成功`
10. ry 申请售后（退货退款）→ `申请已提交`
11. admin 审核通过（**故意伪造 `handler=forged-hacker`**）→ `审核完成`，余额 **440 → 500**，库存 **3 → 5**（回滚一致）
11.1 复核售后单：库中审核人为 `admin`，前端伪造值被忽略
12. 防超卖：库存 1 的商品下单 2 件 → 拦截「库存不足」
13. C2C 卖方：ry（学生）发布商品 → 200 成功，卖家强制为本人（伪造 `sellerId=99` 仍落库为 2）
14. 权限收敛：ry 调售后审核接口 → 403（防自审自批）

**断言校验**：
- PASS 商品发布服务端强制卖家身份：伪造 sellerId=99 → 落库为 1
- PASS 支付扣款金额正确：60
- PASS 订单列表归属过滤：ry 仅返回本人订单
- PASS 余额回滚一致：500.0 == 500.0
- PASS 库存回滚一致：5
- PASS 防超卖生效：库存 1 下单 2 件被拦截
- PASS C2C 卖方：ry 发布商品成功且卖家身份强制为本人(2)
- PASS 权限收敛：ry 调用售后审核（管理员接口）返回 403
- PASS 审核人防伪造：请求传 `handler=forged-hacker` → 库中审核人仍为 `admin`（取自登录态）

> 结论：业务一致性、资金与库存回滚、防超卖、越权拦截均符合预期。

## 四、防超卖专项说明
`CampusProductMapper.decreaseStock`：
```sql
UPDATE campus_product SET stock = stock - #{count}, version = version + 1
WHERE id = #{id} AND stock >= #{count}
```
- 并发场景下，只有 `stock >= count` 的更新能成功（影响行数=1），其余返回 0 → 服务层抛异常并回滚，从根本上杜绝超卖。
- 已被 E2E 用例（库存1、下单2件）验证拦截。

## 八、已知限制与生产建议
- 支付为**沙箱模拟**，无真实第三方支付对接（符合实验「模拟支付」要求）。
- **C2C 卖方能力已对买家角色开放**：`sys_role_menu` 已为角色 2 补授 `campus:product:add/edit/remove`（2100~2102），学生可自主发布并维护自己的商品；后端仍强制「卖家本人或管理员」才能修改/删除，越权无效。
- **发行 jar 已由 Maven 重建**：`ruoyi-admin.jar` 由 `mvn -DskipTests clean package`（Maven 3.9.9 + JDK 17）产出，外层 jar 无手工注入 class，改动类位于内层 `BOOT-INF/lib/ruoyi-system-3.9.2.jar`。此前源码树因 `ruoyi-system` 缺失编译期 `jakarta.validation` 依赖而无法 `mvn compile`（164 处报错），已补入 `spring-boot-starter-validation` 修复。交付包已内置 Maven 与离线依赖仓库，**无网环境亦可从源码重建**。
- **数据库初始无演示数据**：交付库的 campus 业务表已清空（仅保留分类主数据），首次演示前请重跑 `1-初始化数据库.bat` 或导入 `sql/campus_tao_full.sql` 回灌初始数据。
- 演示环境关闭了登录验证码（`sys_config` 置 `false`），生产需开启。
- 仅商品/分类/评价的**列表与详情**读接口保留 `@Anonymous`（便于未登录浏览商品）；其余读写接口均要求登录，且做归属校验（非管理员只能访问本人数据）与权限字符串校验。
- JWT 密钥已支持环境变量注入 `${JWT_SECRET:...}`，交付包内为演示默认值，生产务必通过环境变量覆盖。
- 并发防超卖依赖数据库行锁/乐观锁，未做分布式锁（单机若依足够）。

## 九、补充验证：前端全菜单页面走查（v1.0.1，2026-10-15）
**现象**：系统管理、系统监控下页面点击后内容区空白，仅首页正常。
**根因**：`vite/plugins/auto-import.js` 的自动导入遗漏 `useDict`/`selectDictLabel`。视图在 `<script setup>` 中裸调用 `useDict(...)`，运行时 `ReferenceError: useDict is not defined` 使 setup 中断——页面壳与侧边栏仍在、内容区空白。`main.js` 仅将其挂为 `globalProperties`：模板可用，脚本块不可用。
**修复**：补全自动导入（`@/utils/dict`: `useDict`；`@/utils/ruoyi`: `selectDictLabel`、`selectDictLabels`）。
**走查结果**（重新登录 + 硬刷新后逐页访问，均无 console error）：

| 分组 | 页面 | 结果 |
|---|---|---|
| 系统管理 | 用户/角色/菜单/部门/岗位/字典/参数/通知公告/操作日志/登录日志 | 全部正常渲染 |
| 系统监控 | 在线用户/定时任务/数据监控/服务监控/缓存监控/缓存列表 | 全部正常渲染 |
| 校园淘 | 商品管理（其余页面此前已确认正常） | 正常渲染 |

- 静态复核：Vite 对 17 个受影响模块（含 `system/user/view`、`monitor/operlog/detail`、`system/role/authUser` 等子页面/弹窗）输出的脚本均已注入 `utils/dict`。
- 菜单清理：删除「若依官网」（`sys_menu` menu_id=4）后，重新登录侧边栏不再出现该项。
- 遗留提示：缓存列表页控制台有 `Cannot read Redis info` 警告（演示环境未启用 Redis 监控），不影响渲染。
- 路由备忘：「日志管理」是目录，操作日志/登录日志的实际地址为 `/system/log/operlog`、`/system/log/logininfor`（不是 `/monitor/...`）。
