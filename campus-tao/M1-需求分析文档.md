# 校园淘 · M1 需求分析文档

> 项目：校园淘（校园二手交易平台） ｜ 基础框架：若依 RuoYi-Vue 3.9.2 ｜ 里程碑：M1 需求分析
> 交付说明：本文档对应「实验四」里程碑 M1，是后续技术选型、开发、加固与测试的输入依据。

---

## 一、项目背景与目标

### 1.1 背景

校园场景下，学生手中存在大量闲置物品（教材、电器、生活用品、数码配件等），传统交易依赖宿舍楼栋口张贴、班级群转发与线下私下沟通，存在以下痛点：

- 信息分散，物品曝光与检索效率低；
- 价格与成色不透明，买卖双方沟通成本高；
- 交易缺乏统一记录，资金与物品交割无凭据，纠纷难以处理。

校园淘旨在以校内二手交易为落点，提供一个**覆盖发布到售后的完整交易闭环**的 Web 平台，让闲置物品在同学之间高效、安全地流转。

### 1.2 项目目标

1. 为学生提供「发布 → 浏览 → 加购 → 下单 → 支付 → 发货 → 收货 → 评价 → 售后」的完整闭环能力。
2. 以沙箱支付账户与售后退款机制保障买卖双方的模拟资金安全与可追溯。
3. 通过库存防超卖、订单状态机与事务一致性设计，保证并发交易下数据正确。
4. 在业务功能之外，交付一套满足任务书「≥6 项企业级能力」要求的加固实现（安全、一致性、可靠性、性能、工程化、运维六个维度）。

### 1.3 范围

- **范围内**：校园淘业务模块（商品、分类、购物车、订单、支付账户、售后、评价）及其企业级加固；基于若依原生框架的后台管理能力（用户、角色、菜单、日志、监控等）作为平台底座一并交付。
- **范围外**：真实第三方支付通道对接、真实物流对接、移动端原生 App、分布式多实例部署（本实验为单机发行包形态）。

## 二、干系人与角色

### 2.1 干系人

| 干系人 | 关注点 |
|--------|--------|
| 在校学生（买家） | 分类浏览、加购比价、下单支付安心、售后有保障 |
| 在校学生（卖家） | 快速发布、上下架管理、卖出后收款 |
| 平台管理员 | 商品与分类治理、售后仲裁、系统监控与权限管理 |
| 实验评审方 | 业务闭环完整性、企业级能力覆盖度、可运行与可交付 |

| 编号 | 用例 | 参与者 | 前置条件 | 主流程 | 后置条件 |

| UC-10 | 支付 | 买家 | 订单待付款 | 调用支付 | 沙箱余额扣减，订单进入已付款/待发货 |
| UC-11 | 发货 | 卖家 | 订单已付款 | 调用发货 | 订单进入已发货 |
| UC-12 | 确认收货 | 买家 | 订单已发货 | 确认收货 | 订单进入已完成 |
| UC-13 | 取消订单 | 买家 | 订单待付款 | 取消 | 订单进入异常态，库存回补 |
| UC-14 | 评价 | 买家 | 订单已完成/已收货 | 提交评分与内容 | 生成评价记录 |
| UC-15 | 充值 | 买家 | 已登录 | 沙箱充值 | 账户余额增加 |
| UC-16 | 申请售后 | 买家 | 已有订单 | 提交售后（类型） | 生成售后单待审核 |
| UC-17 | 审核售后 | 管理员 | 有售后审核权限 | 审核通过/驳回 | 通过则退款并回补库存 |
| UC-18 | 查看订单 | 买家/管理员 | 已登录 | 查询订单列表 | 买家仅见本人订单 |

### 3.2 用例细化（关键用例）

**UC-09 下单**
- 触发：买家在购物车勾选商品后点击「去结算」。
- 业务规则：
  - 归属人取自服务端 `SecurityUtils`，前端无法篡改买家身份；
  - 库存扣减与订单落库在同一事务内完成，库存不足则整体回滚；
  - 订单号以 `CT` 为前缀生成，订单项记录成交单价快照。

**UC-10 支付**
- 触发：买家对「待付款」订单点击「支付」。
- 业务规则：
  - 扣款原子化：`UPDATE campus_account SET balance=balance-? WHERE user_id=? AND balance>=?`，余额不足影响行数为 0，拒绝扣款；
  - 支付幂等：对已付款订单重复支付直接返回成功；
  - 状态机约束：仅待付款订单可支付，非法跃迁直接拒绝。

**UC-17 审核售后**
- 触发：管理员在售后管理页对售后单审核。
- 业务规则：
  - 审核通过时，退款（余额回滚）与库存回补在同一事务内完成；
  - 审核权限 `campus:aftersale:edit` 仅授予管理员，普通买家调用返回 403，防止自审自批。

### 3.3 接口域与权限字符串

| 接口域 | 用途 | 权限字符串（写接口） |
|--------|------|----------------------|
| `/campus/product` | 商品 | `campus:product:list/add/edit/remove` |
| `/campus/category` | 分类 | `campus:category:list/add/edit/remove` |
| `/campus/cart` | 购物车 | `campus:cart:list/add/edit/remove` |
| `/campus/order` | 订单 | `campus:order:list/add/edit` |
| `/campus/account` | 支付账户 | `campus:account:balance/edit` |
| `/campus/aftersale` | 售后 | `campus:aftersale:list/add/edit` |
| `/campus/review` | 评价 | `campus:review:add` |

> 写接口统一使用 `@PreAuthorize("@ss.hasPermi('...')")`，无权限返回 403。

### 3.4 订单状态机

```
0 待付款 → 1 已付款/待发货 → 2 已发货 → 3 已完成
                     ↘ 4/5/6 异常态（取消/售后中等）
```

状态跃迁由服务层强约束，非法跃迁（如对非待付款订单支付）直接拒绝。

## 四、非功能需求

### 4.1 安全（Security）

| 编号 | 需求 | 实现要点 |
|------|------|----------|
| NFR-S1 | 登录鉴权 | Spring Security + JWT；未认证请求被拦截 |
| NFR-S2 | 接口授权 | 写接口 `@PreAuthorize`，无权限返回 403 |
| NFR-S3 | 身份不可篡改 | 当前用户身份一律取自服务端 `SecurityUtils`（getUserId/getUsername/isAdmin）；下单/支付/评价归属人不可被前端篡改 |
| NFR-S4 | 数据归属校验 | 订单/购物车/售后/账户接口校验归属，非管理员只能访问本人数据 |
| NFR-S5 | 验证码可配置 | 登录验证码开关由 `sys_config.sys.account.captchaEnabled` 控制，演示环境置 false |
| NFR-S6 | 密钥可注入 | JWT 密钥支持环境变量注入 `${JWT_SECRET:演示默认值}` |
| NFR-S7 | 异常不泄露 | 全局异常处理返回统一 code/msg，避免堆栈外泄 |

### 4.2 一致性（Consistency）

| 编号 | 需求 | 实现要点 |
|------|------|----------|
| NFR-C1 | 事务边界 | 下单、支付、取消、发货、确认收货、售后审核均 `@Transactional(rollbackFor = Exception.class)` |
| NFR-C2 | 库存与订单一致 | 库存扣减与订单落库同事务 |
| NFR-C3 | 资金与库存一致 | 取消/退款时余额回退与库存回补同事务 |

### 4.3 可靠性（Reliability）

| 编号 | 需求 | 实现要点 |
|------|------|----------|
| NFR-R1 | 防超卖 | 乐观锁 `UPDATE campus_product SET stock=stock-?, version=version+1 WHERE id=? AND stock>=?` |
| NFR-R2 | 支付幂等 | 对已付款订单重复支付直接返回成功 |
| NFR-R3 | 防超扣 | 原子扣款 `UPDATE campus_account SET balance=balance-? WHERE user_id=? AND balance>=?` |
| NFR-R4 | 状态机约束 | 订单状态非法跃迁直接拒绝 |

### 4.4 性能（Performance）

| 编号 | 需求 | 实现要点 |
|------|------|----------|
| NFR-P1 | 缓存 | Redis 承担验证码/令牌/系统配置缓存，降低数据库压力 |
| NFR-P2 | 分页 | MyBatis 物理分页（`BaseController.startPage()`） |
| NFR-P3 | 连接池 | Druid 连接池管理数据库连接 |

### 4.5 可维护性（Maintainability）

| 编号 | 需求 | 实现要点 |
|------|------|----------|
| NFR-M1 | 分层清晰 | `com.ruoyi.campus` 独立包，domain/mapper/service/controller/dto/exception 分层，不污染若依原生代码 |
| NFR-M2 | 统一响应 | 统一 `AjaxResult`（code/msg/data） |
| NFR-M3 | 参数校验 | DTO + Jakarta Bean Validation（`@Validated` + `@Valid`，含中文校验提示） |
| NFR-M4 | 异常兜底 | 业务异常统一抛框架 ServiceException；`@RestControllerAdvice` 低优先级兜底未预期的 RuntimeException |
| NFR-M5 | 可观测运维 | 存活探针以鉴权接口返回 200 为准（原生未引入 Actuator）；关键步骤日志留痕；启动期打印端口与内嵌 Redis 状态 |

## 五、数据需求

### 5.1 数据库

- 库名：`campus_tao`。
- 组成：若依 33 张系统表 + 8 张业务表。
- 建表脚本：`sql/campus_tao_full.sql`（全量：DROP + 重建全部表，含业务表与菜单/角色数据）。

### 5.2 业务表清单（8 张）

| 表 | 说明 | 关键字段 |
|----|------|----------|
| `campus_category` | 商品分类（树形） | name、parent_id、sort |
| `campus_product` | 二手商品 | title、price、original_price、condition_level（成色 1-5）、images、stock、seller_id、seller_name、status（0 下架/1 上架）、version（乐观锁） |
| `campus_cart` | 购物车 | user_id、product_id、quantity |
| `campus_account` | 支付账户 | user_id、user_name、balance（沙箱余额）、freeze |
| `campus_order` | 订单主表 | 订单号（CT 前缀）、status、金额、买卖双方 |
| `campus_order_item` | 订单明细 | order_id、product_id、数量、成交单价快照 |
| `campus_aftersale` | 售后单 | order_id、类型、审核状态 |
| `campus_review` | 评价 | order_id、product_id、评分、内容 |

### 5.3 数据一致性约束（业务层约定）

- `campus_product.version` 用于乐观锁，扣库存时同步自增；
- `campus_order_item` 保存成交单价快照，避免商品后续改价影响历史订单；
- `campus_account` 余额变更依赖带条件的原子 UPDATE，账户行不存在时由业务首次充值创建。

## 六、约束与假设

### 6.1 约束

1. **运行平台**：仅支持 Windows 10/11（发行包内置的 Redis 为 Windows 版本，Mac/Linux 需另行处理）。
2. **安装路径**：发行包必须解压到**纯英文路径**，MySQL 在 Windows 上不认中文路径，会截断路径导致启动失败。
3. **端口占用**：依赖 3306（MySQL）、6379（Redis）、8080（后端）、8088（前端 dev）四个端口，需确保未被占用。
4. **前端运行依赖**：前端 `npm run dev` 需本机已安装 Node.js 22（后端与数据库不需要）。
5. **技术底座**：在若依 RuoYi-Vue 3.9.2 之上增量开发，业务代码集中于 `com.ruoyi.campus` 独立包。

### 6.2 假设

1. 支付为沙箱模拟，不涉及真实第三方支付通道。
2. 演示环境关闭登录验证码以便验收，生产环境需开启。
3. 单机部署即可满足实验并发可靠性要求（防超卖依赖数据库乐观锁，未引入分布式锁）。
4. 前端通过 Vite 代理将 `/dev-api` 转发到后端 8080，演示与联调均在本地完成。
