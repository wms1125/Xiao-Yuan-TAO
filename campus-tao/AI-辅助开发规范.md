# 校园淘 · AI 辅助开发规范

> 适用范围：校园淘（campus-tao）交付包全部开发活动 ｜ 版本：v1.0.15 ｜ 生效日期：2026-10-16
> 本规范约束"AI 参与开发"的**边界、留痕、门禁与举证**四件事，使 AI 产出可被人工审查、可被机器验证、可被评审方独立复现。
> 关联文档：`M4-企业级能力加固.md`（六维能力）、`M5-测试报告与交付物.md`（验证证据）、`CHANGELOG.md`（版本变更）、`ai-log/`（过程留痕）。

---

## 一、目的与适用范围

### 1.1 目的

任务书对交付提出「**AI 辅助过程留痕**」的硬性要求。但"用了 AI"本身不是加分项——**能被验证的 AI 产出才是**。本规范要解决三个具体问题：

1. **边界问题**：AI 可以做什么、绝对不可以做什么，避免"AI 写完就直接算完成"。
2. **留痕问题**：每次 AI 参与的决策、踩坑、验证结果如何结构化沉淀，而不是散落在聊天记录里。
3. **举证问题**：如何证明"测试真的在测、门禁真的会拦、修复真的生效"，而不是自说自话。

### 1.2 适用范围

- 覆盖：校园淘后端（`campus-tao/RuoYi-Vue-master`）、前端（`campus-tao-ui`）、SQL 脚本、CI 流水线、文档与演示数据。
- 覆盖：任何由 AI 生成或修改的代码、配置、脚本、文档。
- 不覆盖：纯人工手写的第三方脚手架（若依）原始代码。

## 二、基本原则

| 原则 | 含义 | 落地要求 |
|------|------|----------|
| **P1 · 人在环内** | AI 是执行者，人（开发者/评审者）是决策者与验收者 | 每一处 AI 产出提交前必须经人工审查；架构选型、数据模型、交付形态等决策由人拍板 |
| **P2 · 产出即证据** | 只有通过门禁的产出才算"完成" | 见第五章质量门禁；未过门禁的改动不得进入 `main` |
| **P3 · 自述不算证据** | AI 或文档声称"已完成/已修复/已通过"一律不作为验收依据 | 验收只认三类证据：**可复现的命令输出**、**测试用例**、**独立复算的数据**（见第六章） |
| **P4 · 单一事实来源** | 同一事实（阈值、路径、版本、口径）只在一处定义 | 阈值在 `pom.xml` / `vitest.config.js`；版本在 `pom.xml` + `package.json`；建库在 `campus_tao_full.sql` |
| **P5 · 留痕可追溯** | 每个里程碑/版本都有结构化留痕 | `ai-log/NNN-*.md`（过程）+ `CHANGELOG.md`（结果） |

## 三、AI 参与的分工边界

### 3.1 AI 可以承担（鼓励）

- 按既定技术栈**实现业务代码**（controller / service / mapper / domain / DTO / 前端页面）；
- **编写测试**（JUnit / Vitest / E2E 脚本）与**负向验证**用例；
- **补全工程化配置**（CI、代码规范、覆盖率门禁、构建脚本）；
- **编写文档**（里程碑文档、CHANGELOG、留痕）；
- **排查问题**（读日志、定位报错根因、给出修复方案）；
- **批量、机械性重构**（统一 DTO 校验、清理死代码、格式规范化）。

### 3.2 AI 不可单独决定（必须人工确认）

- 技术选型变更（框架、中间件、数据库）；
- 数据模型 / 表结构破坏性变更；
- 交付形态与部署方式变更（如引入 Docker、Flyway 等会改变交付行为的方案）；
- 安全策略变更（鉴权方式、密钥管理、对外暴露面）；
- 门禁阈值的**下调**（棘轮只允许上调，下调需书面理由）。

### 3.3 明确禁止（红线）

- ❌ 用 AI 生成的内容**替代**真实测试与真实验证；
- ❌ 在**未审查**的情况下把 AI 代码直接提交到 `main`；
- ❌ 向 AI 提交**真实密钥、口令、生产连接串、个人隐私数据**；
- ❌ 把"AI 说可以了"写进验收结论；
- ❌ 让 AI 直接改动**生产环境配置**或执行不可逆的数据操作。

## 四、留痕规范

留痕分两层：**过程留痕**（`ai-log/`）与**结果留痕**（`CHANGELOG.md`）。两者缺一不可。

### 4.1 过程留痕：`campus-tao/ai-log/`

- **命名**：`NNN-<主题>.md`，三位递增编号（当前 `001`~`026`）。
- **头部元信息**（固定格式）：

  ```
  > 里程碑：<Mx（分块）> ｜ 主题：<一句话> ｜ 记录方式：AI 辅助留痕
  ```

- **单篇结构（五段式，必须齐全）**：

  | 段落 | 内容要求 |
  |------|----------|
  | **里程碑目标** | 这一段要解决什么问题、为什么现在做 |
  | **关键决策与取舍** | 表格：决策点 / 选择 / 备选方案 / **取舍理由**（要写"为什么不用备选"） |
  | **踩坑与解决** | 表格：现象 / 根因 / 解决。**根因必须写到机制层**，不能只写"改了就好" |
  | **验证证据** | 可复现的命令 + 真实输出（通过数、覆盖率数字、退出码）；含**负向验证** |
  | **未纳入本轮（如实记录）** | 明确写出本轮**没做**什么、遗留什么风险 |

  > 参照样例：`ai-log/017-前端组件测试与覆盖率棘轮.md`（含负向验证 A/B 与"未纳入本轮"）。

- **诚实性原则**：无法取得可信证据的结论必须**如实标注"未验证"**，不得写成"已确认"。示例（`ai-log/017` 原文）："**CSS 文字错行修复的浏览器视觉验证仍未完成**……故不能声明'页面实测确认'"。

- **元数据块（P2-11 起，每篇必填）**：文件末尾附机器可读的 HTML 注释块，供
  `tools/ai_log_index.py` 校验并汇总到 `ai-log/index.json`：

  ```
  <!-- ai-log-meta
  ai_generated_ratio: 0.9        # AI 生成占比，撰写者自估值
  human_edits: 人工修改内容概述   # 人改了什么（方向、取舍、验收）
  reviewer: 签核人                # 人工复核者；未经复核前如实写"待人工签核"
  review_date: YYYY-MM-DD        # 签核日期；未签核写"待签核"
  -->
  ```

  历史篇目（001~025）无法追溯真值，统一如实标注「未追溯」——**宁可缺失可见，
  不可编造填充**；`ai_log_index.py` 会把签核覆盖度统计进 index.json，差异一目了然。
  校验方式：`python campus-tao/tools/ai_log_index.py --check`（结构不合规退出码 1）。

### 4.2 结果留痕：`CHANGELOG.md`

- 遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) + [语义化版本](https://semver.org/lang/zh-CN/)。
- 每个版本至少含三段：**新增 / 变更 / 修复**，并按需追加 **验证** 与 **未纳入本轮**。
- **版本号三处同步**：后端 `info.app.version`、前端 `package.json` `version`、`CHANGELOG.md` 条目标题。
- 描述必须**可核验**：写清文件路径、命令、阈值、实测数字，而非"优化了性能"这类空话。

### 4.3 留痕与产出的对应

| 交付项 | 留痕位置 |
|--------|----------|
| 需求 | `M1-需求分析文档.md` |
| 选型与环境 | `M2-技术选型与环境搭建.md` |
| 业务闭环 | `M3-业务闭环实现与前端交付.md` + `ai-log/003~006` |
| 企业级加固 | `M4-企业级能力加固.md` + `ai-log/007~010` |
| 测试与交付 | `M5-测试报告与交付物.md` + `ai-log/011~017` |
| 版本变更 | `CHANGELOG.md` |

## 五、质量门禁（AI 产出必须通过）

AI 生成的代码**不区分来源**，一律与人工代码执行同一套门禁。任一门禁失败即视为**未完成**。

### 5.1 后端门禁

| 门禁 | 命令 | 判定 |
|------|------|------|
| 编译 | `mvn -B -DskipTests clean package` | 退出码 0 |
| 单测 + 覆盖率 + 代码规范 | `mvn -B verify` | 退出码 0；Jacoco **行 ≥ 55% / 分支 ≥ 40%**（统计范围 `com/ruoyi/campus/**`，排除 `domain/**`、`mapper/**`）；Spotless 检查通过 |

### 5.2 前端门禁

| 门禁 | 命令 | 判定 |
|------|------|------|
| 格式 | `npm run format:check` | 退出码 0 |
| 全仓静态检查 | `npm run lint` | **0 error**（脚手架遗留 warn 不阻断） |
| **自有代码严格检查** | `npm run lint:strict` | **0 warning**（仅 `src/views/campus`、`src/api/campus`、`src/utils/ruoyi.js`、`tests`） |
| 单测 + 覆盖率 | `npm run test:coverage` | 退出码 0；阈值 **行 40 / 分支 45 / 语句 45 / 函数 55** |
| 生产构建 | `npm run build:prod` | 退出码 0 |

> **为什么分两档 lint**：若依脚手架自带 161 条历史 warn，若要求全仓 0 warning 则永远无法达标；但若完全不设限，新代码的告警会混进噪声被长期忽略。故全仓守 0 error，**自有目录额外守 0 warning**，把质量口径钉在"我们写的代码"上。

### 5.3 端到端门禁

| 门禁 | 命令 | 判定 |
|------|------|------|
| 业务闭环回归 | `python campus-tao/e2e_business.py` | 输出 `RESULT: ALL_PASS`（25 步 / 28 断言全通过） |

### 5.4 一键执行与 CI

- **本地**：`verify.bat`（仓库根）串联上述全部环节，全通过退出码 0。
- **CI**：`.github/workflows/ci.yml` 四个 job（`backend` / `e2e` / `frontend` / `security`）在 `ubuntu-latest` 上执行等价检查；`e2e` job 用 `mysql:8.0` + `redis:7` service 容器跑真实 SQL 与 E2E。
- **一致性要求**：`verify.bat` 与 CI 的检查项必须保持同步，任何一方新增门禁时另一方同步补齐。

## 六、验证与举证要求

AI 声称"已完成"时，必须同时给出以下**三类证据**，缺一不可。

### 6.1 正向验证

- 测试**数量与结果**：`X/X 全绿`，含新增用例数；
- 覆盖率**实测值**与阈值对照（数字来自 `target/site/jacoco/jacoco.csv` 与 `coverage/lcov.info`，非估计）；
- 门禁命令的**退出码**。

### 6.2 负向验证（强制）

**证明"测试真的在测、门禁真的会拦"**——这是 AI 辅助开发最容易被跳过、也最关键的一环。要求：

1. **改坏源码 → 用例必须失败**：临时删除/篡改被测行为，确认对应用例由绿转红，再改回并确认恢复全绿；
2. **门禁必须能被触发**：以超阈值参数运行（如 `--coverage.thresholds.lines=90`），确认退出码非 0；
3. **确认零残留**：负向验证后以 `git diff` / `git status` 确认源码无遗留改动。

> 样例：`ai-log/017` 的负向验证 A（覆盖率门禁触发退出码 1）与 B（删掉 `pageNum = 1` 归位逻辑 → 用例失败）。

### 6.3 独立复算

- **不以被评估方自述为准**：覆盖率、测试数、CI 状态等关键指标，必须从**原始产物**（CSV / lcov / CI 运行记录）**独立复算**，而非引用 CHANGELOG 里的结论；
- **交叉验证**：跨平台（Windows 本地 vs Linux CI）结果不一致时，以 CI 为准并排查差异根因；
- **数据来源可指**：任何数字都要能回答"从哪个文件、哪条命令得到的"。

## 七、上下文与提示词规范

为避免 AI 产生"看起来合理但事实错误"的产出：

1. **先给事实，再给任务**：把相关文件路径、接口签名、表结构、现有约定先喂给 AI，而不是让它猜。
2. **单一事实来源**：阈值、路径、版本等只在仓库中定义一处，提示词中引用该处，不在提示词里另写一份（避免漂移）。
3. **要求给出依据**：让 AI 说明"为什么这样做、依据是什么文件/文档"，便于人工核验。
4. **小步提交**：一次改动聚焦一个主题，避免大范围改动难以审查与回滚。
5. **不确定就说不确定**：要求 AI 明确区分"已验证"与"推测"，推测结论必须标注待验证。

## 八、安全与合规红线

| 项 | 要求 |
|----|------|
| 密钥 | 配置中**不得内置默认口令**，缺失即启动失败（fail-fast）；本地演示值由启动脚本显式注入，生产走环境变量 |
| 敏感信息 | 不得向 AI 提交真实密钥、生产连接串、个人隐私数据 |
| 依赖安全 | 新增依赖须过 `npm audit`（生产依赖 0 告警）与 `osv-scanner`（后端），豁免项须留据 |
| 鉴权 | 涉及数据归属的操作，**身份一律取自登录态**，不接受前端传入的身份参数（如 `sellerId`、`handler`） |
| 越权 | 前端隐藏不等于后端放行；接口须有 `@PreAuthorize` 兜底并有越权断言覆盖 |

## 九、提交前检查清单（Checklist）

AI 参与的任何改动，提交前逐项确认：

- [ ] 代码已**人工审查**（不是"AI 说没问题"）
- [ ] `mvn -B verify` 通过（后端改动时）
- [ ] `npm run format:check` / `lint` / `lint:strict` / `test:coverage` / `build:prod` 通过（前端改动时）
- [ ] `python e2e_business.py` 输出 `ALL_PASS`（涉及业务闭环时）
- [ ] 新增行为**有对应测试**，且做过**负向验证**（改坏会失败）
- [ ] 覆盖率**只升不降**（棘轮）
- [ ] 已追加 `ai-log/NNN-*.md`（含决策、踩坑、验证证据、未纳入本轮）
- [ ] 已更新 `CHANGELOG.md`，版本号三处同步
- [ ] 无密钥/敏感信息入库
- [ ] `git status` 干净，无调试残留、无未跟踪的临时文件

## 十、违规与例外处理

- **门禁失败**：不得以"临时跳过"方式合入；确需临时跳过的，须在 `CHANGELOG` 的"未纳入本轮"中书面记录原因与后续计划。
- **阈值下调**：棘轮阈值原则上只升不降；确需下调的，须给出书面理由并经确认。
- **例外留痕**：任何对规范的偏离，都必须在留痕中显式声明，**不允许静默例外**。
- **追溯**：留痕与 CHANGELOG 是本规范的可审计证据，评审方可据此独立复现全部结论。
